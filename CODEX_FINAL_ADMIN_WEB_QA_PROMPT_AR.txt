============================================================

2. ممنوع استبدال المشروع بنسخة قديمة أو نسخ ملفات من أرشيفات سابقة.
3. اعرض أولًا:
   - المسار الحالي.
   - `git status`.
   - آخر Commit إن وجد.
   - إصدار Node وnpm.
   - إصدار المشروع من `package.json`.
4. أنشئ Git branch منفصلًا باسم واضح مثل:
   `qa/final-admin-web-audit`
   أو اعمل نسخة احتياطية كاملة إن لم يكن المشروع داخل Git.
5. قبل أي تعديل، احفظ Baseline يتضمن:
   - قائمة جميع الملفات الحالية.
   - نتيجة Build والاختبارات قبل التعديل.
   - Screenshots أساسية للعربي والإنجليزي على Desktop وMobile.
6. لا تطبع أو تحفظ أو تكشف أي Secret أو API Key أو Service Role Key أو SMTP password أو Token في Logs أو التقارير أو Screenshots.

9. لا تعدّل بيانات الإنتاج ولا تحذف مستخدمًا أو متجرًا حقيقيًا.
10. أي اختبار كتابة يستخدم حسابات وسجلات تجريبية واضحة، ثم ينظف البيانات التي أنشأها فقط.
11. لا تستخدم:
    - `ignoreBuildErrors`
    - تعطيل TypeScript أو ESLint
    - `@ts-ignore` أو `@ts-expect-error` لإخفاء مشكلة دون سبب موثق
    - `any` عشوائيًا لإخفاء الأخطاء
    - حذف اختبار فاشل أو تخفيف Assertion حتى ينجح
    - `try/catch` فارغ
    - Mock بدل وظيفة حقيقية في مسار الإنتاج

7) بطاقة «الصفحة دي بتعمل إيه؟»

- شرح كل صفحة مختلف ومحدد، ويجيب بوضوح:
  1. الصفحة دي بتعرض إيه؟
  2. صاحب المشروع يقدر يعمل منها إيه؟
  3. القرار أو الإجراء ده بيأثر على إيه؟
- الشرح وافي لكن مختصر، لا يزيد بلا داعٍ ولا يكون عامًا مثل «يمكنك إدارة البيانات».
- اختبر كل مفاتيح PageGuide، وأكد عدم وجود صفحة تستخدم شرح صفحة أخرى أو Fallback عام بلا داعٍ.

============================================================
9) صفحة الشكاوى — اختبار خاص وحاسم
============================================================

الهدف: مسؤول الشكاوى يرى السياق كاملًا ومنظمًا، وليس Transcript متجمعًا داخل رسالة واحدة.

اختبر شكوى محولة من محادثة دعم تحتوي على الأنواع التالية:

- `user`
- `bot`
- `system`
- `support_agent`
- رسائل `support_complaint_messages` بعد إنشاء الشكوى

يجب أن تعرض الصفحة أقسامًا منفصلة بهذا الترتيب:

1. رسائل العميل قبل الشكوى.
2. رسائل البوت.
3. رسائل النظام والتحويل.
4. ردود الدعم قبل تحويلها إلى شكوى.
5. رسائل الشكوى الرسمية.

داخل كل قسم:

- كل رسالة Card/فقاعة مستقلة، لا `string_agg` في العرض.
- اسم المرسل أو وصف واضح للبوت/النظام.
- نوع المرسل.
- التاريخ والوقت.
- ترتيب زمني تصاعدي.
- نص الرسالة كما أُرسل بدون دمج مع الرسالة التالية.
- Empty state واضح لو القسم فارغ.
- العربي والإنجليزي صحيحان.
- النصوص المختلطة Arabic/English لا تنقلب أو تتداخل.

اختبر مسارين للربط:

أ) شكوى حديثة تحتوي:
`support_complaints.admin_action.conversation_id`

ب) شكوى قديمة تم استبدال `admin_action` عند حلها، ويتم إيجاد المحادثة من:
`chat_conversations.metadata.complaint_id`

تأكد أن تسجيل حل الشكوى بعد الآن يدمج `admin_action` الجديد مع القديم ولا يمسح `conversation_id`.

تأكد أن:

- أثناء تحميل السياق لا يظهر النص المجمع القديم لحظيًا.
- الشكوى المنشأة يدويًا، التي لا تملك محادثة سابقة، تعرض نص الشكوى الطبيعي ولا تعرض أقسامًا وهمية.
- لا تتكرر رسالة التحويل الرسمية داخل قسم ما قبل الشكوى بالغلط.
- إرسال رد رسمي جديد يظهر في قسم الرسائل الرسمية بعد نجاح العملية.
- تغيير الشكوى بسرعة لا يعرض رسائل الشكوى السابقة بسبب Race condition؛ تحقق من Abort/Request identity.
- الصلاحية تُفحص على السيرفر، ولا يمكن لمستخدم غير مصرح له استدعاء `complaint_context` مباشرة.
- لا يتم تحميل أكثر من حد معقول دون Pagination أو حد موثق.
